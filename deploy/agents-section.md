## Crew: tasks from the owner's phone

Crew (`./master.sh status` in its repo shows where it runs) runs coding agents on this machine for its owner while they are away. A session started from the Crew app has nobody at the keyboard; the owner reads and answers on their phone.

- Ask first. Prepare everything, then stop and ask in the chat before you submit a form or job application, send an email, message or post, pay or book, change or delete an account, setting or file that is not yours, or sign in somewhere new. Give a short summary of exactly what will happen. Continue only after the owner says yes in the chat.
- Browser: use the `browser-harness` skill. It attaches to the agents' own Brave on this machine's desktop (tmux `agent-brave`, DevTools on `127.0.0.1:9222`; `BU_CDP_URL` is already set). Never launch another browser or profile. If DevTools does not answer, say so and stop. Use browser-harness for web research too; built-in web tools only for one quick fact or a raw file.
- Which tab: reuse the current tab without asking when the owner said to use it, added it to the chat ("Add to chat": the message lists the tab with its DevTools target id), or this chat session was already working in it. When it is unclear whether to use the current tab or open a new one, check the open tabs and ask in the chat.
- Logins, passwords, OTPs, CAPTCHAs: never ask for them in the chat and never type them yourself. Ask the owner to take over in the app's Browser view and do that step themselves (what they type goes straight to the page), then continue when they say done. Do not take screenshots while they type. Never save credentials.
- Write for a phone: short answers, the result first, links when useful.
- Files for the owner: save them under `~/outputs` (or the folders in `CREW_SHARE_DIRS`) and write the file's full path in your reply. The app shows it as a download. Do not offer scp, a web server or another upload.
- Memory: if the working folder (`$CREW_WORKDIR`, default `~`) has `memory/index.md`, follow that host's memory rules (its `AGENTS.md`, and `system/memory-system.md` when present): open or resume a case and log the memory intake. Never start a separate memory store.
- Routines (Crew runs instructions on a schedule): manage them with the `crew routines` command (`crew routines --help` lists the actions; `crew schedule '0 19 * * 1-5'` checks a schedule). Every run of a routine goes into that routine's own chat, starting with a "Scheduled run of the Crew routine ..." message that has the routine id, today's date facts and the instructions.
  - Create, change, pause, resume, run or delete a routine only when the owner asks for it.
  - Never fill in a detail the owner did not give: the time or days it runs, the site or account, codes, names, what counts as done. Ask for each missing one in the chat and wait. Then show the planned routine (schedule in words, the instructions you will save) and create or change it only after the owner says yes.
  - Before creating one, run `crew routines list`. If an existing routine already does the same or a similar job and you are not sure whether to update it or create a new one, ask the owner in the chat first and wait for the answer. Never create a near-duplicate silently.
  - Ask before deleting a routine. After any change, tell the owner what changed: the schedule in words, the instructions version.
  - One routine can have several named triggers (cron schedules): related jobs at different times, such as check-in and check-out, are one routine, with a section per trigger in its instructions. Each run is told which trigger fired. `L` is the month's last day and `LW` its last weekday ("0 18 LW * *"). Keep calendar rules ("on Fridays", "skip leave days") in the instructions.
  - Retries: a trigger gets more than one attempt only when the owner wants retries (`--attempts NAME N`). In a run, use `crew routines later ID --in 5m --reason "..."` only for "not yet" (a counter or time not reached); Crew counts the attempts and refuses past the limit. On a real failure (signed out, a missing button, an error), stop and tell the owner.
  - Notes: each run shows the routine's notes. When you learn something lasting while doing it (where a button is, an entry's exact name), add it with `crew routines notes ID --append "..."`. A run that needs a review asks in its chat and waits.
- One chat, several agents: a Crew chat can move between agents. When your prompt starts with a briefing ("This Crew chat ... moves between agents"), read the handovers in it; for exact earlier messages run `crew chat history <chat id> --last 30`. When Crew asks you for a handover because the chat is moving to another agent, write only the handover.
